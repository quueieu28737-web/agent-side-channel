能站住的部分：
- 以"result record"而非论文为单位的证据绑定框架。它能暴露 Dangol 的 stored 与 live 记录、Early Bird 的两个机制这类被混淆的比较，这是真正有用的 SoK 视角。
- “state-changing calls 承载主信号，而 prompt 规则只改变读序”这一机制性发现，具体且反直觉。
- 把 trace path 与 action path 放进同一条 agent–tool 链路来评估。
会被质疑的部分：
1. Remark 1 是教科书级 DPI，不是贡献。建议降格为一句话，不要编号。
2. 防御组件几乎都有先例。 影子/诱饵查询来自 WRA，常速率隧道来自 IP-TFS/RFC 9347，桶化填充和常形状来自 WF 防御（Tamaraw、FRONT 等）。论文 4.2 节自己也承认 E5 “not claiming it as new”。审稿人会问：新的到底是什么？
3. 身份危机。 它同时想当 SoK（82 家族、39 记录）、方法论论文（三个 check）、实证论文（690 + 4,140 次）和防御论文（shadow shaping）。每一块都"够用但不极致"。S&P 的 SoK 要求有明确的 systematization insight，而 RQ1–RQ4 在正文中没有被逐条回答。
4. SoK 部分的方法学弱点： 
   - 初稿由 AI 辅助，作者验证。κ 是"抽取 vs 验证"的一致性，不是独立评分者信度，论文自己也承认。
   - 语料是 purposive 的，且无召回估计。
   - 24 个 rule-application 案例由作者构造，只检验规则应用，不检验准确率。
优点： 690 次真实 agent 运行；训练/测试按客户分离；defense calibration 仅用训练集；TLS 重放有解析模型校验；E13 加入了 timing 和完整隧道对照。
关键缺口（按杀伤力排序）：
A. Headline 与 cross-fit 不自洽。
- 摘要和贡献写"降到 50%"，但 Table 10 中同一个 E9 constant 设计在 cross-fit 下是 60.5%/52.1%。
- Rules + joint 在冻结测试集上是 50.0/60.6，仅 prompt 不同就差 10 点。这说明估计量噪声很大，50% 是有利的一次实现。
- 测试集只有 5 个 cancel 阳性客户、7 个 return 阳性客户，CI 为 [50, 60.6] 和 [50, 65.5]，绝对阈值（BA 上界 <0.60）没有任何一个关键 cell 通过。
- 论文自己写了 “do not certify the absolute bound”，但摘要没有对应的收敛。
B. 单环境、单模型、单别名。 只有 τ-bench retail，一个可变的模型别名，同一模型兼任用户模拟器，且开发阶段见过全部 115 个任务。泛化性完全靠自述。
C. 攻击者偏弱，且没有真正的 defense-aware 自适应攻击。
- 攻击套件是 GBDT/LR 加手工特征（计数、bigram、长度）加计数规则。
- 没有序列模型（CNN/Transformer/LSTM）、没有 k-FP 类 WF 攻击，也没有知晓防御设计和参数分布的攻击者。
- 防御者校准时知道总体分布（"known-population calibration"），这对防御有利。
D. “utility 不受损”是构造出来的，不是测出来的。 Reward 在四个程序条件下完全相同，因为是对同一轨迹重放，论文也承认 “equal reward is structural”。真正的 RQ4（端到端 utility）在真实 agent 上没有被回答。E13 虽然 live 执行，但轨迹仍是固定的，没有 timing-dependent replanning。
E. 缺少与标准防御的同口径 Pareto 对比。 没有把 Tamaraw/FRONT/WTF-PAD 等适配到同一批 E9 轨迹上，因此"新方案处于什么前沿"无法判断。唯一对照是 constant framing 和完整隧道。
F. 成本不实用，却声称 “actionable”。 12 到 15 倍字节、3.8 倍调用、隧道 125.7 倍；serial shadow 在 timing 视角下还泄漏（+11.4 点）。E13 结论是没有任何一个配置满足绝对准则。
G. 威胁模型落地性。
- 谁是 agent→tool 链路上的被动观察者？
- 多个 tool 端点时，SNI/IP/ECH 已经泄露工具身份，shadow 的收益是否仍成立？
- 信任的 shadow executor/gateway 本身就是新的信任点，provider 的 commit log 也在范围外。
- 诱饵调用带来的计费、限流和 DoS 放大没有讨论。
H. 规则 prompt 是稻草人。 它本来只约束读序，当然不会隐藏意图。"behavioral compliance ≠ metadata protection"这一点成立，但分量被夸大成一个主要 takeaway。
I. E10–E12 是 post hoc。 E11 的"操作点选择"是回溯性的，作者自己也说不是独立确认。
- 4.2 节写"pre-registered tests"，而第 8 节只说"七个作者构造的机制检查在 E5–E7 之前记录"，这是 overclaim。
- 正文依赖 S1–S19 十余次，但审稿人没有义务读补充材料，主文必须自足。
- Table 8 的 “?”（intentional）读起来像偷懒。为什么不联系作者或复现？
- Table 9（BA 97.2/94.0，276 episodes）、Table 10（91.7/85.5，690 episodes）、Table 11（91.7/86.4，138 trajectories）的 “undefended” 数字口径不同，读者很容易混淆。
- 摘要数字密度过高，结构上不像摘要。
T1. 把 cross-fit 提升为主结果，改写 headline
1. 以 690 次的 customer-grouped cross-fit 作为 primary result，冻结 46 任务测试集降为 confirmatory/sanity。
2. 摘要和贡献改为：undefended 91.7/85.5 → 联合方案 52–60%，配对下降 31–47 点；"50%" 仅作为冻结测试集上的点估计出现一次并附 CI。
3. 全文统一一个术语表：undefended / baseline / raw 只用一个。

T2. 增加第二个环境和第二个模型
1. 环境：τ-bench airline（同框架，改动最小），或一个 MCP 文件/Git 类工具集，状态改变调用的结构要不同。
2. 模型：至少一个开源权重模型（固定版本，可复现）和一个不同厂商的闭源模型，替换"可变别名"。
3. 规模：不必重做 690 次，每组 ≥150 次且保证阳性客户数足够即可。
4. 用两个新环境/模型检验 E12 的"write calls 承载信号"是否复现，这是最有价值的泛化检验。
5. 验收标准：主要定性结论（规则无效、writes 主导、联合 shaping 显著降低）在 ≥2 个额外设置中复现。若不复现，如实报告并收窄 claim。
T3. 解决统计功效问题
1. 做功效分析：为让 BA 上界 <0.60 的绝对准则有机会通过，需要多少阳性客户。

T4. 强化攻击者
